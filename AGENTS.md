# AGENTS.md

Notes for coding agents working on Lander NTP. Start with [README.md](README.md) for what the extension is. Read [CONTEXT.md](CONTEXT.md), the glossary, and use its terms in code, comments, docs and PRs.

## Working in this repo

- A WXT + Preact browser extension for Chrome, Firefox and Edge. The source is in `src/`. The new tab page (`src/entrypoints/newtab`) is the whole product; the background script (`src/entrypoints/background.ts`) only records whether this is a new install or an update.
- Before you finish, run `npm run typecheck`, `npm run lint`, `npm run format:check` and `npm test`. `npm run build:all` builds all three browsers, and `npm run lint:firefox` checks the Firefox build.
- PR titles follow Conventional Commits (`feat:`, `fix:`, `chore:` …), because release-please builds the changelog from them.
- Branches and PRs: work for a phase lands on its phase branch, `phase/<n>-<name>` (for example `phase/1-foundations`), and reaches `main` only when the phase is done. A build ticket's branch is `lr-<ticket number>-<slug>`, and its PR targets the phase branch (`gh pr create --base phase/<n>-<name>`; `gh` picks `main` otherwise), or its parent's branch when stacked. PRs into a phase branch merge with a merge commit; stacked PRs merge bottom-up, parent before child. Fixes released from `main` reach a phase branch through a sync PR, `chore: Merge main into phase/<n>-<name>`, from a branch like `sync/main-into-phase-<n>` that merges `origin/main` into the phase branch; a phase branch is never rebased. Build PRs never edit `CHANGELOG.md`, the `version` in `package.json` or `.release-please-manifest.json`; release-please owns them.
- Stored settings are checked against their current shape (`src/settings/storage.ts`). Changes to what is stored are additive only: a new field or item is optional and worked out from what is stored, or from its defaults. New checks keep what they do not recognise and write it back unchanged. While devices on 0.2.x may still sync, nothing in `sync:settings` is removed or widened (no value v0.2.3 does not know), no key is added inside a block, and its `clock` and `weather` blocks keep the shape v0.2.3 reads; from phase 2 they are frozen apart from `clock.hour12`. v0.2.3 replaces settings it cannot read with the defaults, and its next save writes them to every device. The same compatibility keeps the whole-settings fallback in `src/settings/storage.ts` (settings that fail the check become the defaults) as it is. There is no migration code, and WXT's `version` and `migrations` are not used. From phase 2 `sync:settings` and `sync:layout` carry a version `v` (`sync:onboarding` does not, until a breaking change needs one). A missing `v` is 1, which is what v0.2.3 wrote; nothing is written on update or on load, and the first save after an update adds `v: 1`. A device never saves over an item whose `v` is higher than it knows (or whose `v` it cannot read): `defineGuardedItem` in `src/storage/guard.ts` looks at what is stored when it writes, throws `NewerVersionError` and writes nothing, and the page shows that item read-only. When the shape changes, update the check and its tests.
- Onboarding lives in `src/onboarding`. A new install gets the welcome and a tour of the settings (`TOUR` in `callouts.ts`); an update gets the callouts in `NEWS`, once each. To announce a feature, add an entry to `NEWS` with a new `id` and, if it needs a new spot on the page, a `callout--<section>` rule in `style.css`.
- Widgets: each Widget is a folder in `src/widgets/` holding its `definition.ts` (`type`, never renamed or reused; `name`; options as data; needs; source), its View, tests and stories. The parts they share are in `src/widgetSystem/`. A Widget reads only its own options and the page-wide values (`PageValues`). Its option keys follow the additive rule for stored settings above.
- Storybook (`.storybook/`) is for looking at the page's parts, not for testing them: in this phase the Vitest suite is the only tests. Stories sit beside their component as `*.stories.tsx`. Widget and settings stories use the `withPage` decorator (`.storybook/withPage.tsx`), which gives them the page wrapper and the toolbar's font; `App` stories don't, as `App` draws both itself. Stories seed storage (WXT's fake browser, reset before each story) and never touch the network: use the fixtures in `src/test/fixtures.ts` (`STORY_PHOTOS`, `makeWeather`, `makePlace`). Story photos are the three small real ones in `.storybook/public/story-photos/` (credits in `STORY_PHOTOS`); `public/fallback.webp` is the extension's own. `App` stories seed a whole page state with `seedPage(PAGE_SEEDS.<name>)` (`src/test/seed.ts`), and `src/test/seed.test.tsx` checks each seed against the same `PAGE_SEEDS`. When stories or what they draw change, run `npm run storybook:build` too.
- Chromatic publishes Storybook (`.github/workflows/chromatic.yml`) with `disableSnapshot`, so no visual tests run. Every PR description carries its branch link, `https://<branch>--6ad582e200912f972f91511a.chromatic.com`, once the PR's first run has published. Per Chromatic's docs, characters a subdomain can't hold in the branch name become dashes, dashes collapse, and 37 characters is the most; the docs don't say what happens to digits, so copy the link from Chromatic rather than working it out by hand. The run log's "View your Storybook" line is that build's own link and doesn't contain the branch. Links need a Chromatic sign-in while the project's Storybook visibility is private.
