# AGENTS.md

Notes for coding agents working on Lander NTP. Start with [README.md](README.md) for what the extension is. Read [CONTEXT.md](CONTEXT.md), the glossary, and use its terms in code, comments, docs and PRs.

## Working in this repo

- A WXT + Preact browser extension for Chrome, Firefox and Edge. The source is in `src/`. The new tab page (`src/entrypoints/newtab`) is the whole product; the background script (`src/entrypoints/background.ts`) only records whether this is a new install or an update.
- Before you finish, run `npm run typecheck`, `npm run lint`, `npm run format:check` and `npm test`. `npm run build:all` builds all three browsers, and `npm run lint:firefox` checks the Firefox build.
- PR titles follow Conventional Commits (`feat:`, `fix:`, `chore:` …), because release-please builds the changelog from them.
- Branches and PRs: work for a phase lands on its phase branch, `phase/<n>-<name>` (for example `phase/1-foundations`), and reaches `main` only when the phase is done. A build ticket's branch is `lr-<ticket number>-<slug>`, and its PR targets the phase branch (`gh pr create --base phase/<n>-<name>`; `gh` picks `main` otherwise), or its parent's branch when stacked. PRs into a phase branch merge with a merge commit; stacked PRs merge bottom-up, parent before child. Fixes released from `main` reach a phase branch through a sync PR, `chore: Merge main into phase/<n>-<name>`, from a branch like `sync/main-into-phase-<n>` that merges `origin/main` into the phase branch; a phase branch is never rebased. Build PRs never edit `CHANGELOG.md`, the `version` in `package.json` or `.release-please-manifest.json`; release-please owns them.

- Stored settings are checked against their current shape (`src/settings/storage.ts`). Changes to what is stored are additive only: a new field or item is optional and worked out from what is stored, or from its defaults. New checks keep what they do not recognise and write it back unchanged. While devices on 0.2.x may still sync, nothing in `sync:settings` is removed or widened (no value v0.2.3 does not know), no key is added inside a block, and its `clock` and `weather` blocks keep the shape v0.2.3 reads; from phase 2 they are frozen apart from `clock.hour12`. v0.2.3 replaces settings it cannot read with the defaults, and its next save writes them to every device. The same compatibility keeps the whole-settings fallback in `src/settings/storage.ts` (settings that fail the check become the defaults) as it is. There is no migration code, and WXT's `version` and `migrations` are not used. From phase 2 `sync:settings` and `sync:layout` carry a version `v` (`sync:onboarding` does not, until a breaking change needs one). A missing `v` is 1, which is what v0.2.3 wrote; nothing is written on update or on load, and the first save after an update adds `v: 1`. A device never saves over an item whose `v` is higher than it knows (or whose `v` it cannot read): `defineGuardedItem` in `src/storage/guard.ts` looks at what is stored when it writes, throws `NewerVersionError` and writes nothing, and the page shows that item read-only. When the shape changes, update the check and its tests.
- `src/sync/shapes/` is shared with the sync server and must stay pure: Valibot and other pure relative imports only, with no WXT, browser, DOM or locale access.
- The Layout (see `CONTEXT.md`) is one synced item, `sync:layout`, versioned by `v` and the same on every device; its code is in `src/layout`. Unknown data is kept at every level. A Layout whose `v` is higher than this version knows, or that cannot be read at all, is read-only: draw the parts this version understands, but save no changes. `useLayout(settings)` gives the stored Layout or, derived until first changed, the one `deriveLayout` (`src/layout/derive.ts`) works out from today's settings while `sync:layout` is empty: nothing is written until the first `commit`, which stores all of it and never touches `sync:settings`. v0.2.3 never reads it, and phase 2 writes Layout changes there and never to `sync:settings` (the rows in `PHASE_2_WRITES`, `src/test/compat/compat.test.ts`, guard that). Callers of `useLayout` gate `commit` on `loaded`: the write-time guard only protects a newer or unreadable Layout, so a commit before the stored one has arrived can overwrite a normal one. `App` draws the Layout through `Grid` (`src/components/Grid`) once both the stored settings and the Layout have loaded; every Widget is drawn in a `WidgetBox` at the cells `drawnRects` gives it (never its stored place), in reading order, keyed by its id. Removing a Widget (×, Delete or Backspace) is `removeWidget` and one `commit`, so one write to `sync:layout` and none to `sync:settings`: removing the Clock never writes `clock.enabled`. The Undo notice holds the removed Widget in memory only (`useRemovalController`, `src/widgetSystem/useRemoval.tsx`); its options are not stored anywhere, `waiting` included, and are gone with the notice.
- Onboarding lives in `src/onboarding`. A new install gets the welcome and, from "Show me around", the guided tour (`TOUR` in `callouts.ts`; new installs only, an update never sees it): Edit, move and resize, options, the setup button, Add and Done on the page, then Photos and the font in the settings panel (its two sections; the Clock's and the Weather's options are on their widgets). `planTour` (`tour.ts`) picks the stops the page has from `pageFacts`: the stops about a widget go from an empty Grid, and the setup button has its own stop only when a widget is waiting for setup, else the Add stop says it (the Add stop's note sits beside the menu's first item, not the Add button, which the open menu would be covered by). `PageTour` (`components/Callout`) draws the page's stops: Next does each thing for the person, through `useEditMode` and the Add menu's handle (`useAddMenuControl`, which opens the menu without moving focus off the note's button), and nothing on the Grid changes or is stored; the welcome's answer (`answerWelcome`) is the one write. Whatever the tour put on, edit mode and the Add menu, goes when it ends, whether dismissed, finished or ended by hand; leaving edit mode by hand or opening the settings ends the run; a stop whose target is not on the page after `MISSING_MS` is skipped, and a Layout that cannot be changed (a newer version wrote it) has no stop that tells the person to change something (`changes` on a stop; its Edit stop says to update instead). When the run ends focus goes to the Edit button (or, at the end of the settings panel's stops, its Close button), not the page. A note keeps clear of the photo credit and the Bottom bar (`keepClear` in `placeBeside`) and, for a setup button, sits beside its widget's frame. An update gets the callouts in `NEWS`, once each (at the moment one, `layout`, at the Edit button, whose "Show me" enters edit mode; a new install has it recorded as seen. That button is the `showMe: 'edit'` field of a page callout, handled by `PageNews` in `components/Callout`: another action for a later entry goes there, and a dismissal is always `dismissNews`, which only gains an id. The `weather` one opened a settings tab that is gone, so it was removed, and its id in anyone's `dismissed` list is harmless; do not reuse it). To announce a feature, add an entry to `NEWS` with a new `id`. A callout either has a `section` of the settings panel, which keeps its fixed spot (a `callout--<section>` rule in `style.css`; there is none now, as the settings panel's own tour is drawn inside the panel and no news points at a section), or a `target` on the page (`edit`, `add`, `menu:<type>`, `widget:<type>`, `options` or `setup`; see `CalloutTarget` in `target.ts`), which needs no CSS: the element carries `data-callout-target="<target>"`, whoever builds a new button or menu item adds that attribute, and the callout is placed beside it by `placeBeside` with a pointer and no ring (`components/Callout/useBeside.ts`). A callout whose target is not on the page is not drawn, and a run of stops skips it (`nextShown`).
- Widgets: each Widget is a folder in `src/widgets/` holding its `definition.ts` (`type`, never renamed or reused; `name`; `sizes`; `summary`; `credit`; options as data; needs; source), its View, tests and stories. The parts they share are in `src/widgetSystem/`. A Widget reads only its own options and the page-wide values (`PageValues`). Its option keys follow the additive rule for stored settings above.
- Storybook (`.storybook/`) is for looking at the page's parts, not for testing them: in this phase the Vitest suite is the only tests. Stories sit beside their component as `*.stories.tsx`. Widget and settings stories use the `withPage` decorator (`.storybook/withPage.tsx`), which gives them the page wrapper and the toolbar's font; a lone Widget also gets the box the page gives it with `withBox` (`decorators: [withBox, withPage]`, its cells in `parameters.box`). `App` stories don't use either, as `App` draws all of it itself; the Viewport menu has four windows: the two the Grid is judged at, 1440 by 900 and 1366 by 768, a phone's 390 by 800, and a short 1366 by 400 for the options popover (`.storybook/preview.tsx`). Stories seed storage (WXT's fake browser, reset before each story) and never touch the network: use the fixtures in `src/test/fixtures.ts` (`STORY_PHOTOS`, `makeWeather`, `makePlace`). Story photos are the three small real ones in `.storybook/public/story-photos/` (credits in `STORY_PHOTOS`); `public/fallback.webp` is the extension's own. `App` stories seed a whole page state with `seedPage(PAGE_SEEDS.<name>)` (`src/test/seed.ts`), and `src/test/seed.test.tsx` checks each seed against the same `PAGE_SEEDS`. When stories or what they draw change, run `npm run storybook:build` too.
- Each Widget in `src/widgetSystem/registry.ts` needs, in `src/widgets/<Name>/*.stories.tsx`, `<Name>/Ready` stories at Smallest, Starting and Largest and an `AllSizes` story. With a `source` it also needs `Loading` and `Failed` at those sizes. For each need that has a label and an action it needs `<Name>/Setup/<Need>` at those sizes. `src/widgets/stories.test.ts` enforces this.

- Chromatic publishes Storybook (`.github/workflows/chromatic.yml`) with `disableSnapshot`, so no visual tests run. Every PR description carries its branch link, `https://<branch>--6ad582e200912f972f91511a.chromatic.com`, once the PR's first run has published. Per Chromatic's docs, characters a subdomain can't hold in the branch name become dashes, dashes collapse, and 37 characters is the most; the docs don't say what happens to digits, so copy the link from Chromatic rather than working it out by hand. The run log's "View your Storybook" line is that build's own link and doesn't contain the branch. Links need a Chromatic sign-in while the project's Storybook visibility is private.
- Store listings, data-disclosure forms and release notes are refreshed by the owner from the checklist in `docs/store-listing-refresh.md`; no listing is published from the repo.

## Agent skills

### Issue tracker

Issues and the widget roadmap live in the **Lander roadmap** Notion database, not GitHub Issues. See `docs/agents/issue-tracker.md`.

### Triage labels

Canonical label names, split across two Notion select properties (`Category`, `Triage`). See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: `CONTEXT.md` at the repo root for the glossary; decisions (ADRs) live as `grilling` tickets in the Lander roadmap Notion database. See `docs/agents/domain.md`.
