# AGENTS.md

Notes for coding agents working on Lander NTP. Start with [README.md](README.md) for what the extension is. Read [CONTEXT.md](CONTEXT.md), the glossary, and use its terms in code, comments, docs and PRs.

## Working in this repo

- A WXT + Preact browser extension for Chrome, Firefox and Edge. The source is in `src/`. The new tab page (`src/entrypoints/newtab`) is the whole product; the background script (`src/entrypoints/background.ts`) only records whether this is a new install or an update.
- Before you finish, run `npm run typecheck`, `npm run lint`, `npm run format:check` and `npm test`. `npm run build:all` builds all three browsers, and `npm run lint:firefox` checks the Firefox build.
- PR titles follow Conventional Commits (`feat:`, `fix:`, `chore:` …), because release-please builds the changelog from them.
- Branches and PRs: work for a phase lands on its phase branch, `phase/<n>-<name>` (for example `phase/1-foundations`), and reaches `main` only when the phase is done. A build ticket's branch is `lr-<ticket number>-<slug>`, and its PR targets the phase branch (`gh pr create --base phase/<n>-<name>`; `gh` picks `main` otherwise), or its parent's branch when stacked. PRs into a phase branch merge with a merge commit; stacked PRs merge bottom-up, parent before child. Fixes released from `main` reach a phase branch through a sync PR, `chore: Merge main into phase/<n>-<name>`, from a branch like `sync/main-into-phase-<n>` that merges `origin/main` into the phase branch; a phase branch is never rebased. Build PRs never edit `CHANGELOG.md`, the `version` in `package.json` or `.release-please-manifest.json`; release-please owns them.
- Stored settings are checked against their current shape (`src/settings/storage.ts`). Changes to what is stored are additive only: a new field or item is optional and worked out from what is stored, or from its defaults. New checks keep what they do not recognise and write it back unchanged. While devices on 0.2.x may still sync, nothing in `sync:settings` is removed or widened (no value v0.2.3 does not know), no key is added inside a block, and its `clock` and `weather` blocks keep the shape v0.2.3 reads; from phase 2 they are frozen apart from `clock.hour12`. v0.2.3 replaces settings it cannot read with the defaults, and its next save writes them to every device. The same compatibility keeps the whole-settings fallback in `src/settings/storage.ts` (settings that fail the check become the defaults) as it is. There is no migration code, and WXT's `version` and `migrations` are not used. From phase 2 every synced item carries a version `v` (`sync:layout` first), and a device never saves over an item whose `v` is higher than it knows. When the shape changes, update the check and its tests.
- Onboarding lives in `src/onboarding`. A new install gets the welcome and a tour of the settings (`TOUR` in `callouts.ts`); an update gets the callouts in `NEWS`, once each. To announce a feature, add an entry to `NEWS` with a new `id` and, if it needs a new spot on the page, a `callout--<section>` rule in `style.css`.
- Storybook (`.storybook/`) is for looking at the page's parts, not for testing them: in this phase the Vitest suite is the only tests. Stories sit beside their component as `*.stories.tsx`. Widget and settings stories use the `withPage` decorator (`.storybook/withPage.tsx`), which gives them the page wrapper and the toolbar's font; `App` stories don't, as `App` draws both itself. Stories seed storage (WXT's fake browser, reset before each story) and never touch the network: use the fixtures in `src/test/fixtures.ts` (`STORY_PHOTOS`, `makeWeather`, `makePlace`). Story photos are not `public/fallback.webp` but the three small real ones in `.storybook/public/story-photos/`, with their credits in `STORY_PHOTOS`. `App` stories seed a whole page state with `seedPage` (`src/test/seed.ts`), which `src/test/seed.test.tsx` checks. When stories or what they draw change, run `npm run storybook:build` too.
